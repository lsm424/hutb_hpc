## 三、可专利性评估

### 3.1 现有技术不能教示的特征

1. **时间对齐缓存优化**：全部7篇对标专利均未提及通过数学对齐查询起始时间戳来稳定索引扫描范围、利用InnoDB Buffer Pool实现缓存复用的技术手段。这属于"非显而易见"的数据库物理层优化。

2. **整数除法桶划分**：现有技术使用浮点除法（FLOOR((ts-start)/interval)）或窗口函数（ROW_NUMBER），均未公开在SQL层使用整数DIV运算避免浮点单元开销的技术方案。

3. **覆盖索引流式聚合的组合应用**：虽然覆盖索引本身是已知技术，但将其与(node, ts, val)特定索引结构、FORCE INDEX、GROUP BY流式聚合结合应用于时序降采样场景，在全部对标专利中未见公开。

4. **关系型数据库零改造约束下的系统级优化**：现有方案要么改造数据库内核（GPU加速）、要么迁移数据到外部系统（Spark），要么在应用层全量加载（LTTB）。本方案在"不改库、不加硬件、不迁移数据"三重约束下实现了高性能，这种约束条件和解决方案的组合在现有技术中未出现。

### 3.2 可授权性判断

- **新颖性**：时间对齐缓存机制 + 整数DIV桶划分 + 覆盖索引流式聚合的三位一体组合，在检索结果中未找到相同或等同公开
- **创造性**：本领域技术人员在面对"如何在不改造MySQL的前提下提升降采样查询性能"这一技术问题时，现有技术的教导方向是"迁移到专用时序库"或"加GPU硬件"，而非"利用缓存对齐优化现有SQL查询"——本方案的技术路线本身即具有非显而易见性
- **实用性**：已在HPC集群监控系统中生产运行，查询响应从500ms降至<100ms

### 3.3 建议保护范围

- **独立权利要求（方法）**：时间对齐 + 整数桶划分 + 覆盖索引流式聚合的完整方法
- **从属权利要求**：覆盖索引结构设计、缓存预热机制、自适应步长、多节点并行采集
- **系统权利要求**：包含上述方法的监控数据查询系统
- **可扩展保护**：权利要求用语宜覆盖 PostgreSQL、ClickHouse 等支持覆盖索引+流式聚合的其他关系型数据库
